# User Story 3.2 — AI Explanation Assistant

## Context

US 3.2 gives a user with no medical background a way to ask for a plain-language
explanation of anything on screen. A partial implementation already exists and
ships today:

- `POST /api/explain` accepts `{ indicator_id, kind }` where `kind` is one of
  `explain` / `why` / `simpler`, and returns `{ reply, source, disclaimer }`.
- Three buttons per indicator in [IndicatorCard.jsx:113-146](../../src/components/IndicatorCard.jsx#L113-L146).
- A single result panel in [Report.jsx:138-164](../../src/pages/Report.jsx#L138-L164),
  held in one `assistant` useState.

Four gaps, one of which is a live defect:

1. Only **indicators** are explainable. 3.2.1 also names statistics and
   recommendations.
2. There is **no way to ask a question** — only three fixed buttons. 3.2.3
   describes a user *asking* for a diagnosis, which nothing today can express.
3. The replies are deterministic string assembly from DB rows — nothing is
   generated — yet the payload already ships the string *"AI-generated
   explanations are educational only…"* ([server.js:231](../../server.js#L231)). That
   claim is currently false, and 3.2.4 turns on it.
4. **Grounding defect (3.2.2).** `/api/explain` calls
   `mortalityFor(indicator_id, { age_group: "40-44" })` while `buildAssessment`
   calls `mortalityFor(item.indicator_id, profile)`. `ageBandFor`
   ([server.js:58-60](../../server.js#L58-L60)) returns `"41-59"` only for age groups
   `45-49` and `50-54`, otherwise `null`. So for a user aged 45–54 the card
   ranks the `41-59` band row first while explain returns an `all`-Malaysia row —
   **the explanation cites a different figure than the one displayed.**

Intended outcome: one explanation surface reachable by button *or* by typed
question, working across indicators, statistics and recommendations, answering
in plain language generated by a model but provably grounded in rows we already
display, declining out-of-scope requests, and disclosing its nature before the
user interacts with it.

## Decisions taken

| Question | Decision |
|---|---|
| Real LLM or deterministic assembly? | **Real LLM, grounded on our rows** |
| Provider | **Google Gemini, free tier** |
| Free-text question box? | **Yes — resolved locally, question never leaves the browser** |
| Conversation history? | **No — single-shot** |
| What goes in the Gemini prompt? | **Published rows only** |
| Which statistics? | **Report page only** — reference value and mortality context inside `IndicatorCard` |
| Cache generated replies? | **Yes** — in-memory, per server |

## The core idea: free text is a resolver, not a second pipeline

The typed question is matched against the user's own report **in the browser**,
resolved to a target, and then handed to the exact same endpoint the buttons
already call. Nothing new is sent anywhere.

```
  BUTTON PATH                        FREE-TEXT PATH
  "Explain this" on an indicator     user types a question
        |                                   |
        |                            checkOutOfScope(question)   <- 3.2.3, in-browser
        |                                   |  hit -> DECLINE_REPLY, no request at all
        |                                   |  pass
        |                            resolveQuestion(question, result)
        |                                   |  no match -> "I can only explain
        |                                   |               what's on your report"
        |                                   |  match
        |                                   v
        +----------------> { target_type, target_id, kind, age_group }
                                            |
                                            v
                              POST /api/explain   (one endpoint, unchanged shape)
                                            |
                              cache hit? -> return, zero quota
                                            |  miss
                              buildContextPack(rows)      <- published data only
                              POST to Gemini
                              verifyGrounded(reply, pack) <- 3.2.2 enforcement
                              checkOutOfScope(reply)      <- 3.2.3, output side
                                            |
                              { reply, source, mode, disclaimer }
```

Three consequences worth stating plainly:

- **The free-text feature adds no API surface.** F1 below is required by 3.2.1
  regardless; free text needs nothing beyond it.
- **The typed question never leaves the browser.** Not to Google, not even to
  our own server. `resolveQuestion` runs client-side against `result`, which the
  client already holds in state.
- **A typed question can return Gemini-written prose** — because the button path
  may already have generated and cached that item's explanation from public rows.
  The user gets fluent model-written text; their words went nowhere.

The trade-off, stated honestly: this answers *"which item are you asking
about?"*, not the literal question. *"Why is smoking ranked above my diet?"*
returns the smoking explanation, not a comparison. That is the price of zero
egress, and it is the right price for a health app on a free tier that trains on
submitted content.

## 🚩 Flagged — raise with the team before implementing

Everything in this section is outside `src/`. Per `CLAUDE.md` nothing has been
written against it.

### F1 — `/api/explain` request shape *(both servers)*

`{ indicator_id, kind }` → `{ target_type, target_id, kind, age_group }`.

- `target_type`: `"indicator" | "reference" | "mortality" | "recommendation"` — required by 3.2.1.
- `age_group`: required by 3.2.2, so the server can call `mortalityFor` with the
  *same* profile band `buildAssessment` used and fix the defect above. Validate
  against the existing `AGE_GROUPS` constant array.

Report.jsx is the only caller, so this is a clean break with no compatibility
shim. **Unchanged by the free-text decision** — the resolver emits this same shape.

### F2 — `/api/explain` response shape *(both servers)*

Add `mode: "generated" | "assembled"` so the panel can be honest about which path
produced the reply, and extend the disclaimer to include *"may contain errors"*
(3.2.4 requires all three elements; the current string has two).

### F3 — Outbound Gemini call from the server *(both servers)* — the big one

New network egress and a third-party dependency in the request path. Needs:

- `GEMINI_API_KEY` and `GEMINI_MODEL` added to `.env.example` and to
  `render.yaml`. `.env` stays gitignored; never commit a real key.
- Endpoint: `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`
- **Send the key as the `x-goog-api-key` header, not `?key=` in the query
  string.** The prototype uses the query string
  (`web/src/lib/agent/llm/provider.ts`), which puts a live credential into proxy
  and access logs. Same API, strictly better hygiene.
- **Model IDs drift and cannot be verified from the assistant's knowledge cutoff** —
  read the current free-tier list off AI Studio and set `GEMINI_MODEL`. Keep the
  prototype's try-configured-then-fall-back pattern as a hedge against a model ID
  being retired under us.
- **Three fallback triggers, one behaviour:** no key, HTTP error (including 429
  quota exhaustion), or `verifyGrounded` failure ⇒ return today's deterministic
  assembly with `mode: "assembled"`. Offline SQLite dev, CI and `npm test`
  therefore need no key and no network.
- **The team should see this explicitly:** the free tier trains on submitted
  prompts and allows human review. The design keeps both user answers *and*
  typed questions out of the prompt entirely — see *What leaves the app*, and
  read that section before signing off on F3.

### F4 — Dependencies: none needed *(resolved)*

Node 22 has global `fetch`, and the call is a single JSON POST — the prototype's
own Gemini branch (`chatText` in `web/src/lib/agent/llm/provider.ts`) is ~40
lines and can be lifted almost directly, minus the tool-calling path we don't
need. **No new dependency, so nothing to approve here.**

### F5 — No auth on a public endpoint *(reframed, low severity)*

Not a billing risk on the free tier — a **shared-quota** risk. Limits are
per-key, so every user of the deployed app draws from one pool.

The cache is the real mitigation: the key space is bounded and small, so after
warm-up almost every request is a hit and spends no quota. Free text does not
change this — it resolves to the same bounded key space. A light per-session cap
in each server (in-memory token bucket, no dependency) stops one client burning
the cold-cache budget. Quota exhaustion is not an outage: it degrades to
`mode: "assembled"`, the reply we ship today.

### F6 — Optional seed copy *(db/seed.sql, shared)*

3.2.1 requires prose "free of unexplained clinical terminology". Seeded copy
contains *Hypercholesterolaemia*, *NCD screening*, *prevalence*,
*prioritisation*, *medically certified deaths*. The Gemini path can define or
avoid these via the prompt, so this is **not** required on the primary path — but
the deterministic fallback would still emit them raw. Recommend deferring; raise
it only if the team wants the fallback to meet 3.2.1 too.

**No schema change is required for any AC.** `db/schema.sql` and
`db/schema.postgres.sql` are untouched.

## What leaves the app

Google's free tier trains on submitted content. From their
[terms](https://ai.google.dev/gemini-api/terms): *"Google uses the content you
submit to the Services and any generated responses to provide, improve, and
develop Google products and services"*, and *"human reviewers may read,
annotate, and process your API input and output."* The paid tier does neither.
This is the constraint the whole design is built around.

| Sent to Google | Never sent — and never leaves the browser |
|---|---|
| `indicator_name`, `description` | **The user's typed question** |
| `reference_value`, `unit`, `reference_year`, `interpretation` | Lifestyle answers (smoking, sleep, diet, activity) |
| Mortality rows: `cause_name`, `measure_value`, `age_group` band | Family-history categories |
| `action_title`, `action_description`, `explanation`, `first_step` | `gender`, `state` |
| `dataset_name`, `organisation` | `session_id` |

Every field in the left column is already published and already rendered on the
user's screen. The outbound request is indistinguishable from asking about
public NHMS/DOSM statistics.

`age_group` reaches the **server** — 3.2.2 needs it to select the same mortality
rows the card rendered — but it selects rows and never enters the prompt text.
The DOSM band label (`41-59`) may appear in a reply because it is printed on the
card and is a public dataset label, not a personal attribute.

**Enforced, not just intended.** `buildContextPack` is a pure function over row
objects and `test/explain-safety.test.mjs` asserts its output contains no
profile field. The privacy guarantee is a passing test, not a comment.

**Privacy notice** ([Privacy.jsx:128-134](../../src/pages/Privacy.jsx#L128-L134)) gains
one line: explanations are generated by a third-party AI service from published
statistics only, and questions typed into the assistant are matched on your own
device and are not sent anywhere. `src/` change — not flagged.

## Caching

Explanations are deterministic for a given target, so generate each once.

```
key  = `${target_type}:${target_id}:${kind}:${band}`
hit  -> cached reply, zero quota, no network
miss -> Gemini -> verifyGrounded
        pass -> cache and return  (mode: "generated")
        fail -> return assembled, do NOT cache
```

A plain `Map` in each server. No dependency, no schema change, cleared on
restart. 8 indicators × 3 kinds × 4 target types × 2 age bands is a few hundred
entries at most, so it cannot grow without limit and needs no eviction policy.
Both entry paths — button and resolved free text — share the same keys.

## Shared modules

### `src/explain-safety.mjs` *(new)*

Pure functions, no DB and no SQL dialect — the same precedent as
[src/rules.mjs](../../src/rules.mjs), the one module both servers already share.
Imported by **the client and both servers**, so the decline text and the
out-of-scope rules cannot drift between the UI and the API. Vite bundles `.mjs`
for the client without ceremony. Note this bends the "`.mjs` = Node-side"
convention in `CLAUDE.md`; `rules.mjs` sets the precedent for shared logic living
in `src/` and this is the same category.

| Export | Used by | Serves |
|---|---|---|
| `resolveQuestion(question, result)` | client | matches a typed question to a target; returns `null` on no match |
| `checkOutOfScope(text)` | client (question) + servers (reply) | **3.2.3**, both directions |
| `DECLINE_REPLY` | client + servers | **3.2.3** — states it cannot give medical advice *and* directs to a qualified professional |
| `buildContextPack(rows)` | servers | published-rows-only prompt input |
| `verifyGrounded(reply, pack)` | servers | **3.2.2** enforcement |

`verifyGrounded` extracts every number from the model's reply and asserts each
appears in the context pack; a failure discards the whole reply rather than
patching it. **The prototype has no equivalent — this is the key adaptation.** It
is also provider-agnostic, which is why switching from Anthropic to Gemini cost
nothing structurally: only the ~40-line transport changed.

`resolveQuestion` scores the question's tokens against `indicator_name`, the
recommendation titles and the cause names present in `result` — the user's own
report, a closed set of ~10–40 rows. It also infers `kind`: *"why"* → `why`,
*"what does that mean" / "simpler"* → `simpler`, otherwise `explain`. All of it
is a pure function, so it is directly unit-testable, which matters because
`node:test` with no jsdom is the only testing capability we have.

### `src/components/ExplanationPanel.jsx` *(new)*

One component for all four ACs. Props: `explanation`, `loading`, `error`,
`onClose`. Renders, in order:

1. **Disclosure block** → **3.2.4**. Visible whenever the panel is open,
   *including while loading*. Keys off `mode` (see 3.2.4 below).
2. `explanation.reply` → **3.2.1**; the decline text renders through the same
   slot → **3.2.3**, no special-casing.
3. `explanation.source` → **3.2.2** provenance.
4. `<Disclaimer>` — reuse [Disclaimer.jsx](../../src/components/Disclaimer.jsx) as-is.

Because the response shape is uniform across every `target_type`, the panel needs
no branching on target type at all.

### Where state lives

Unchanged from the existing pattern — no router, no state library. `Report.jsx`
owns `assistant`, `assistantLoading`, `assistantError`, `question` in `useState`
and threads one `onExplain(target_type, target_id, kind)` callback down. Matches
the `CLAUDE.md` convention: App owns app-wide reads, pages own their own writes.

## Per-AC breakdown

### 3.2.1 — Plain-Language Explanation on Request

**Requires:** an explanation affordance on an indicator, a statistic and a
recommendation; reply in everyday language free of unexplained clinical terms.

| Target | Status | Where |
|---|---|---|
| Indicator | Exists | [IndicatorCard.jsx:113-146](../../src/components/IndicatorCard.jsx#L113-L146) |
| Statistic — reference value | **Missing** | `.comparison-box`, [IndicatorCard.jsx:62-85](../../src/components/IndicatorCard.jsx#L62-L85) |
| Statistic — mortality context | **Missing** | `.mortality-box`, [IndicatorCard.jsx:87-111](../../src/components/IndicatorCard.jsx#L87-L111) |
| Recommendation | **Missing** | `.recommendation-card`, [Report.jsx:188-228](../../src/pages/Report.jsx#L188-L228) |
| Free-text box | **New** | `Report.jsx`, above the panel |

The free-text box is an additional route to the same explanations — it widens
*how* a user can request one, and satisfies the AC's "requests an explanation"
more naturally than fixed buttons alone.

**Files:** `IndicatorCard.jsx`, `Report.jsx`, `ExplanationPanel.jsx`,
`explain-safety.mjs`. **Verdict:** src/ for the UI — **needs F1**.

### 3.2.2 — Grounded in Displayed Content

**Requires:** refers to content already presented; introduces no statistic or
claim outside the app's own data.

Four layers, strongest last:

1. **Resolver** — free text can only ever resolve to a row already in the user's
   report. There is no path to an off-report topic.
2. **Context pack** — built from exactly the rows behind the displayed item,
   reusing `referenceFor`, `mortalityFor` and the recommendations query already
   in both servers.
3. **Prompt** — use only the context; never introduce a number.
4. **`verifyGrounded`** — post-generation numeric check; on failure the reply is
   discarded, not patched.

Plus the **defect fix**: pass the real `age_group` through so `mortalityFor`
returns the same rows the card rendered.

**Files:** `explain-safety.mjs`, both servers. **Verdict:** **needs F1 + F3.**

### 3.2.3 — Out-of-Scope Requests Declined

**Requires:** decline, state it cannot provide medical advice, direct the user to
a qualified healthcare professional.

The free-text box makes this AC properly reachable — a user can now actually ask
for a diagnosis. Two gates, same function:

- **Input** — `checkOutOfScope(question)` runs in the browser before anything
  else. A hit returns `DECLINE_REPLY` with **no network request at all**. This is
  the prototype's design, and here it doubles as a privacy control: a question
  containing a medication or symptom is stopped before it can reach even our own
  server.
- **Output** — `checkOutOfScope(reply)` on Gemini's text catches model-generated
  diagnosis language. The reply is replaced wholesale, not edited; a
  partially-scrubbed diagnosis is still a diagnosis.

Rules must cover all four AC categories: diagnosis, medication/dosage, treatment
plan, and prediction of the user's own outcome. The prototype's
`medical-rules.ts` covers the first two plus stopping medication, and is a useful
starting checklist — it does **not** cover treatment plan or outcome prediction.

**Files:** `explain-safety.mjs`, `Report.jsx`, both servers.
**Verdict:** input gate is src/-only; output gate **needs F3**.

### 3.2.4 — Assistant Nature Disclosed

**Requires:** AI-generated · educational only · may contain errors, at the
beginning of the interaction.

The current string has the first two, is missing *"may contain errors"*, and
appears only *with* the reply rather than at the start. Fix: a static one-line
notice adjacent to the assistant buttons and the free-text box, visible **before**
any interaction, plus the disclosure block inside the panel.

**The claim is not always true**, and that matters here. Replies come back as
`mode: "generated"` (Gemini wrote it) or `mode: "assembled"` (template — no key,
Gemini error, quota exhausted, or `verifyGrounded` failed). A decline is neither.
Claiming "AI-generated" over a template is the same inaccuracy in the other
direction, so **the disclosure keys off `mode`**. This makes F2's `mode` field
load-bearing rather than cosmetic.

**Files:** `ExplanationPanel.jsx`, `IndicatorCard.jsx`, `Report.jsx`, `pages.css`.
**Verdict:** **satisfiable within src/** given `mode` from F2.

## What transfers from the prototype

Source: `jxia0077-boop/sihatq-prototype`, `web/src/`.

**Take:**

- **The free-text input pattern** (`web/src/app/ai-assistant/page.tsx`) — a
  controlled input in a `<form>`, `onSubmit` → `preventDefault` → one shared
  `sendMessage(text)` that trims, guards on `loading`, and clears the field.
  Their suggestion chips call the same function, so chips cost nothing extra;
  we'll do the same with our three `kind` buttons.
- **The input safety gate running before egress** — the single best idea in their
  chat feature, and the reason 3.2.3 is cheap for us.
- **The Gemini transport** — `chatText`'s Gemini branch in
  `web/src/lib/agent/llm/provider.ts` is the closest thing to drop-in code in the
  repo: one JSON POST, `{ systemInstruction, contents }` in,
  `data.candidates[0].content.parts[].text` out, plus a try-each-model fallback
  loop. Take it minus tool-calling; move the key to the `x-goog-api-key` header.
- **The deterministic fallback** — `buildFallbackAnswer` is string concatenation
  from rows, used when every provider fails. That is architecturally what
  `/api/explain` already is, so our existing code becomes the fallback branch.

**Leave:**

- **Their RAG-to-LLM path for free text.** Retrieval grounds the *answer*; it does
  nothing about the *question*, which they send to the model verbatim. Our
  resolver runs locally instead.
- The agent runtime — ReAct loop, plan mode, multi-agent coordinator, memory,
  trace recorder, MCP registry, skills catalog. It orchestrates four tools that
  read four tables.
- The four-provider router (`chatWithTools`, `protocolPref`, the
  Anthropic/OpenAI/Doubao/Ollama branches). One provider, and our fallback is our
  own template, not another vendor.
- Embeddings and pgvector. Our corpus is a closed set of rows selected by ID —
  nothing to search, nothing to embed.
- SSE / streaming, multi-turn history, Supabase auth, `user_id`-keyed storage,
  cross-session memory, Next.js component shape, Tailwind, Material Symbols.
- **The page/widget duplication.** They implemented the same chat twice
  (`ai-assistant/page.tsx` and `AiChatWidget.tsx`, 382 lines, already slightly
  diverged). One component only.

## What must not be carried over

Checked against the four named concerns. Two are not present — reported honestly
rather than manufacturing findings:

| Concern | Finding |
|---|---|
| Hardcoded API keys | **Not present.** Every key is read from `process.env`. |
| Permissive CORS | **Not present.** Same-origin Next.js route handlers; no CORS headers set. Our Express servers set none either. |
| Unvalidated input | **Inverted** — thorough Zod validation. We match it with inline validation and an early `res.status(4xx).json({ error })`, per existing convention. |
| Missing error handling | **Partly real.** The SSE `catch` swallows the error with no logging, so stream failures are invisible in production. `console.error("Anthropic tools error", status, text)` logs raw provider response bodies. |

Two risks that matter more for us and are not on that list:

- **API key in the query string** (F3) — a live credential in every proxy and
  access log along the path.
- **Silent `.catch(() => {})`.** Fine for our existing fire-and-forget writes that
  404 harmlessly on SQLite; **not** fine for the Gemini call, where swallowing the
  error hides both outages and quota exhaustion.

Two of our own to add: **never log question text** (it is the one thing a user
might put personal detail into), and **never log the Gemini response body** on
error.
